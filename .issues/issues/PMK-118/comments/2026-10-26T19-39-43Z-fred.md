## Plan

Spec: `docs/superpowers/specs/2026-10-26-pmk-118-migration-failure-source-design.md`
Plan: `docs/superpowers/plans/2026-10-26-pmk-118-migration-failure-source.md`

Today a failing migration step throws `INVALID_INPUT` "migration X to Y failed: <cause>" with next step `pmkit validate`, and `validate` rethrows the same error.

1. `planMigration` adds `details: { migration: { from, to } }` to that error. Its code, message and next step stay the same, so `migrate` and every command that reads an older-format tracker still exit 2 with it.
2. `brokenConfigProblem` lists an error with `details.migration` as `{ path: '<trackerPath>/config.yaml', code: 'migration', message: <the error message> }`. A new code keeps doctor from treating it as a format or a setting problem. `validateRepo` takes a `migrations` option, used only by tests, and passes it to `loadConfig`.
3. Tests: unit tests through `loadConfig`, `migrate` and `validateRepo` with an injected failing step. A spawned child makes the built-in step throw and checks that `issues list` exits 2 and `validate` exits 0 with the problem. Another test checks that a failing step 2 of 3 leaves the tracker, the version and the git log unchanged.

Two tasks, tests first. No golden should change.
