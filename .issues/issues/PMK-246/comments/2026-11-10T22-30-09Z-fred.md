Decision PMK-246-1 (from the orchestrator): option A, one release per issue.

A Linear issue can be in several releases (`Issue.releases`, `addedReleaseIds`, `removedReleaseIds`), and the pmkit model has one `release` per issue.

- `issues get` shows `release` when the issue is in exactly one release that is not canceled. With two or more, it shows `releases: [ids]` (a Linear-only field, like `delegate`) and no `release`.
- `issues update --release X` (and `none`) swaps the current release for X. On an issue in two or more releases it refuses with INVALID_INPUT, saying how many releases the issue is in and that the change is made in Linear.
- `issues bulk release` follows the same rule, with the same message for every issue it refuses.

The implementer's own calls, which the orchestrator agreed with:

- The pmkit id of a Linear release is its UUID, as for milestones.
- `release list` lists only the releases of pipelines linked to the scope team.
- Canceled releases stay out: they are not listed, not read as an issue's release, and a write to one is refused.
- A release's state is `released` when Linear sets `completedAt`.
- With releases off, `release list` and `release get` answer as PMK-40 decided (an empty answer with a note that says releases are off), and the writes refuse with NOT_SUPPORTED saying releases are off.
- `issues create --release`, `release issues`, `release create` and `release mark-released` stay NOT_SUPPORTED. They are follow-ups.

Option B (one release per pipeline, keeping the releases of other pipelines) is a follow-up if teams with several pipelines ask for it.
