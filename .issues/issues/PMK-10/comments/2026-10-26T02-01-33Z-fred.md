## Plan

Spec: `docs/superpowers/specs/2026-10-25-pmk-10-command-scenarios-design.md`
Plan: `docs/superpowers/plans/2026-10-25-pmk-10-command-scenarios.md`

The open question was how a scenario drives an agent headless. The answer has two parts. A scripted scenario per command file runs in `npm test` with no agent, so it is offline and deterministic. An opt-in live suite (`PMKIT_LIVE=1`) runs the same scenarios with `claude -p` and is the part to cut if the spike shows `-p` cannot run it.

1. Shared helpers: the fake `gh` moves to `scripts/fake-gh.mjs`, `runPmkit` takes stdin and extra env, `hashTree` can skip `.git`.
2. A parser reads each command file's steps, its `pmkit.mjs` calls and its "Confirmation points" bullets. Trace rules check that every write comes after a confirmation and after its own dry run.
3. Static checks over all 24 command files: every call uses a real command and real flags, every write is confirmed, and every command file has a scenario. `commands/issues/summary.md` gets its confirmation point as a bullet.
4. A runner runs each scenario on a fresh fixture copy, records a trace and a snapshot of the changed files, and checks `expect`. Reads and dry runs must leave the tree unchanged. `UPDATE_GOLDENS=1` regenerates the snapshots.
5. to 8. The 24 scenarios, grouped by area. The GitHub path runs on `team` with a bare origin and the fake `gh`.
9. The live spike (at most two `claude -p` runs with a 1 USD cap each), then `scripts/scenarios-live.mjs` if the spike holds.

Text mismatches between a command file and the CLI get fixed here and listed in the PR. No CHANGELOG entry, since the CHANGELOG is written per release.
