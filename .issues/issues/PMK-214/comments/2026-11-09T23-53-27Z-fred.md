## Plan

Spec: `docs/superpowers/specs/2026-11-09-pmk-214-improve-delegate-design.md`. Plan: `docs/superpowers/plans/2026-11-09-pmk-214-improve-delegate.md`.

1. **Native delegation on Linear.** Agent ids on Linear are `agent:<Linear user id>` (stable on rename, match `AGENT_ID`); discovery's `agents` list returns them. The issue fragment reads `delegate { id }` and `toIssue` sets `issue.delegate`. `delegate` checks everything first (key owner, the agent is an app user, the issue exists), then posts the delegation comment and sets `delegateId`, so the agent sees the instructions when Linear starts it. `run: 'native'`. The manifest entry becomes `native` when the workspace has an app user, `absent` with a hint otherwise. `issues track-agents` is listed under `unsupported` on Linear and refuses there (follow-up).
2. **Agent member in the `team` fixture.** `agent:claude` joins the members; the goldens then record a real delegation.
3. **Atomic `delegate`.** Local: one write, comment file first, then `issue.md` and both events with one timestamp; the comment file is removed if the issue write fails. Linear has no transaction: all checks before the first mutation, and a delegate update that fails after the comment returns an error naming what was written and what is missing.
4. **`/pmkit:issues:work --as <agent>`.** The delegated run passes the agent; the readiness check treats that agent as the user, the claim is for the agent and every write carries `--as`. Without `--as`, an issue held by an agent is a readiness problem that names it. The delegation comment and `/pmkit:issues:delegate` step 7 use `--as`.
5. **Contract suite.** The agents family accepts `run` of `local` or `native` and reads the agent from `assignee` or `delegate`. The Linear contract run over the fake adds the family.
