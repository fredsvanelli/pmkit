## Plan

Spec: `docs/superpowers/specs/2026-10-26-pmk-121-velocity-late-close-design.md`
Plan: `docs/superpowers/plans/2026-10-26-pmk-121-velocity-late-close.md`

Decision (rule A): `cycle close` writes a `closed` timestamp on the sprint, right after `state`. Velocity counts an issue moved to `done` up to that moment. A closed sprint without `closed` (closed before this change, or with a malformed value) keeps today's rule, the move date on or before `end`. No old sprint file is rewritten and the format version does not change. Rule B (end plus a grace period) still counts moves after the close, and rule C (a snapshot at close) would freeze estimates.

1. `velocity` in `scripts/lib/metrics.mjs` uses `closed` with the end-date fallback. `metrics velocity` and `/pmkit:cycle:plan` read it, and `/pmkit:report:status` reads no velocity.
2. `parseSprint` reads `closed` and `closeCycle` writes it. A malformed value is not fatal, and `validate` lists it as a `sprint` problem.
3. `/pmkit:cycle:close` step 8 runs the moves and the split before `cycle close`, so a split original moved to `done` counts. A failed write stops the step, a rerun finishes a split already made instead of creating a second issue, and the retro runs only after a successful close. A static test checks that order.
4. The design spec and `CONTEXT.md` describe `closed` and the cutoff.

Five tasks, tests first. The two `cycle-close` goldens and the `cycle-close` scenario snapshot change. They are regenerated with `UPDATE_GOLDENS=1` and the diff is read line by line.
