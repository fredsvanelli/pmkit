Implementation plan (spec: `docs/superpowers/specs/2026-11-10-pmk-217-improve-review-pr-against-issue-design.md`, plan: `docs/superpowers/plans/2026-11-10-pmk-217-improve-review-pr-against-issue.md`).

1. Criterion 2, cut diff by file: `pr diff` returns `files` (`path`, `lines`, `cut`) and takes `--file <path>` to read one file's sections; a path not in the diff is `INVALID_INPUT`. Step 3.2 of `/pmkit:issues:review` reads each cut file one at a time, or marks the criteria that depend on it `not checked`.
2. Criterion 1, comment on the pull request: new write `pr review --issue <id> --body-file f [--comments-file f]` posts one GitHub review (event `COMMENT`, never approve or request changes) with inline comments. Each inline line is checked against the pull request diff before any write, dry run included; a diff GitHub refuses as too large refuses inline comments. GitHub posts the review whole or not at all. The command offers it next to the issue comment, each write asked once.
3. Criterion 3, checks as gaps: the review reads `pr status`; a failing check is a gap, its `ci logs --run` names the failing step, and a criterion whose test fails cannot be `covered`. Pending, cancelled or unreadable checks are `not checked`, never passing.

Tests: `cli-pr.test.mjs`, `github-host.test.mjs`, a diff parser test and the `issues-review` scenario (happy path, plus a cut diff with a failing check).
