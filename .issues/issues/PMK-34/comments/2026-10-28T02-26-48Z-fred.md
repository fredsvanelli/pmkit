# PMK-34 ask for the mappings a hosted tracker cannot infer, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans, as the user picks, to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/pmkit:setup` sets up a Linear repository. `init --tracker linear` infers what it can, returns what it must ask, writes `tracker.scope` and `mappings` after one approval, and every Linear operation except `discover` and `capabilities` stops when a mapping names something the workspace no longer has.

**Architecture:** A generic module `scripts/lib/mappings.mjs` holds the rules (propose, check, parse flags) over an adapter-neutral description. `scripts/lib/linear/mappings.mjs` builds that description from PMK-33's discovery and exposes `resolveMappings`, the reader PMK-35 uses. The Linear tracker runs the check before each operation. `init` gets a hosted branch built on both. `commands/setup.md` drives it with `AskUserQuestion`.

**Tech stack:** Node.js ESM, `node:test`, `fakeLinearFetch` and `fakeWorkspace` from `scripts/fake-linear-api.mjs`, `userStoreEnv()` and `fixedNow()` from `scripts/test-helpers.mjs`.

**Spec:** `docs/superpowers/specs/2026-10-27-pmk-34-ask-for-mappings-design.md`. The user's answers are in its "Answered questions" section.

## Global constraints

- `npm test` opens no socket. Every Linear test injects `fakeLinearFetch`. Every test that reaches the user store sets `PMKIT_HOME` through `userStoreEnv()`.
- `package.json` gains no dependency (ADR-0003).
- Every Local tracker output and every golden stays byte-identical. The Local setup scenarios keep their calls and snapshots.
- The key never appears in output, a file, an error or a command line. Tests use `FAKE_KEY`.
- No file, commit or comment holds the real workspace URL key or team key. Examples use `acme` and `ACME`. Docs say "the sandbox workspace".
- No task sends a write to Linear. Setup sends queries only.
- No Linear name enters `scripts/lib/mappings.mjs`.
- `mappings.types` is the only schema change. Its shape is an object from a pmkit type name to one Linear label name. A type without a label is left out. `types` absent means setup never asked. `types: {}` means it asked and the answer was nothing.
- `resolveMappings(view, pmkit)` keeps its name and return shape (spec, "The mappings contract"). PMK-35 reads through it.
- ADR-0002: every flag a command file names exists in the CLI, every call ends with `--json`, every write call has a confirmation point.
- Every commit message carries `(PMK-34)` and ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Code, comments and messages follow `~/.claude/skills/unslop/SKILL.md`.

## Review focus

1. The setup question limit. `AskUserQuestion` takes four questions per call, and a Linear setup asks up to six (in review, blocked, four types). Task 12 batches them and the scenario in Task 13 covers it.
2. `types: {}` round trip. The writer must emit it, `validatePmkitConfig` must accept it, and a second setup run must not ask again. Task 2 and Task 11 test it.
3. A type label that exists in both the team and the workspace. The team's wins on read and on check (Task 5 and Task 6).
4. The write refusal while questions remain, because criterion 2 must hold for any CLI caller (Task 11).
5. A mapping broken only in a stale cache. The run-time check refreshes once and throws only if the miss persists (Task 9).
