# PMK-36 Linear history and comments implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans, as the user picks, to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the Linear stubs of `getHistory`, `listComments`, `comment` and `metricEvents` with real operations, and add `resolveThread` as a contract operation that the Local tracker implements first and Linear implements second.

**Architecture:** `history.mjs` is pure. It turns a Linear issue node, its history entries and its comments into pmkit events by rewinding from the current issue, and turns a comment node into a pmkit comment. `history-ops.mjs` holds the operations that send requests, built on `issueOperations` (`readNode`, `contextFor`, `requireViewer`, `completeNested`). `documents.mjs` gains six named documents and leaves `ISSUE_FRAGMENT` as it is. The stateful fake records history entries and comments, so the contract suite runs its `history` family against Linear in `npm test`. Local goes first (ADR-0001): optional `reply_to`, `resolved` and `resolved_by` keys in a comment file, the `resolveThread` operation, then the suite, then Linear.

**Tech stack:** Node.js ESM, `node:test`, `node:crypto` `randomUUID`, the PMK-30 client (`request`, `paginate`, `session`), `fakeLinearFetch` from `scripts/fake-linear-api.mjs`.

**Spec:** `docs/superpowers/specs/2026-10-28-pmk-36-linear-history-comments-design.md`

1. A replay of `getHistory` events must equal `getIssue` for title, type, status, priority, estimate, assignee, labels, parent, related and due. Task 10 tests it on seeded entries.
2. History and comments both arrive newest first. The fake serves them that way, so a missing sort fails a test (Tasks 7, 9, 12).
3. A reply to a reply attaches to the root, on Local and on Linear (Tasks 1, 12).
4. A dry run of `comment` and `resolveThread` sends no mutation and returns the shape of the real write (Tasks 12, 13).

  - `ISSUE_HISTORY_QUERY` (`PmkitIssueHistory`): `issue(id) { creator { id } botActor { type name } history(first, after) { nodes { ...entry fields } pageInfo } }`. The first page selects the origin; a later page can select it too and the caller ignores it.
  - `ISSUE_COMMENTS_QUERY` (`PmkitIssueComments`): `issue(id) { comments(first, after) { nodes { ...COMMENT_FIELDS } pageInfo } }`.
  - `COMMENT_BY_ID_QUERY` (`PmkitCommentById`): `comment(id) { ...COMMENT_FIELDS issue { identifier } }`.
  - `COMMENT_CREATE` (`PmkitCommentCreate`): `commentCreate(input: CommentCreateInput!) { success comment { ...COMMENT_FIELDS issue { identifier } } }`.
  - `COMMENT_RESOLVE` (`PmkitCommentResolve`): `commentResolve(id: String!) { success comment { ...COMMENT_FIELDS issue { identifier } } }`.
