# PMK-31 load hosted tracker configs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The loader accepts any `tracker.system` that has an adapter and checks `tracker.scope`, `tracker.scope.workspace` and `mappings`. A system without an adapter still fails with `NOT_SUPPORTED`, and every command reaches the tracker through the contract operations only, awaited.

**Architecture:** A registry in `scripts/lib/adapters.mjs` maps a system to a descriptor. `loadConfig` reads `.pmkit/config.yaml`, then returns a hosted config with no `.issues/` read, or runs today's Local path, now `loadLocalConfig`. The async CLI builds the tracker through the descriptor and hands commands a frozen `contractView`. Local-only features go through `ctx.local()`, which is `null` for any other system.

**Tech Stack:** Node 18+ ES modules, no dependencies (ADR-0003), `node:test`. Run the suite with `npm test`.

**Spec:** `docs/superpowers/specs/2026-10-27-pmk-31-load-hosted-tracker-configs-design.md`. Read it before Task 1. The spec is the authority, except for the points in "Refinements to the spec" below, which planning found and which this plan decides. Report any other difference.

## Refinements to the spec

Planning found these gaps. They are decided here.

1. **`issues dependencies` reads `ctx.config().local`.** It uses `local.epic_prefix` to tell an epic id from an issue id, and `local.estimate.unit` for the map. The spec's table misses both. The unit comes from `(await tracker.discover()).estimate.unit`. The prefix comes from `ctx.settings().epicPrefix`, so a descriptor's `settings(config)` returns `{ defaults, epicPrefix }`. The Local descriptor gives `config.local.epic_prefix`. A hosted descriptor gives `null`, and the command then treats every id as an issue. The discover output does not gain the prefix, because the `discover` goldens would change.
2. **The Local-only check must not load the local config.** `migrate` reads a tracker of any format, and `ctx.config()` refuses a newer format first. `config.mjs` exports `loadPmkitConfig(root, { adapters })`, which runs steps 1 to 4 of `loadConfig` and reads only `.pmkit/config.yaml`. The runner uses it for `local: true` commands. `loadConfig` calls it, then branches.
3. **The helper names.** `groupEventsByIssue`, `categoryLookup` and `sprintIssues` in `scripts/lib/metrics.mjs`. The name `eventsByIssue` stays free, because `runRisks` already has a local variable with that name.
4. **`groupEventsByIssue` key order.** `cycleTimes` and `leadTimes` keep the key order of their input, and the Local `eventsByIssue` orders keys by `compareIds`. The helper sorts keys with `compareIds` from `scripts/lib/ids.mjs`.
5. **The flow metrics read every event.** `doneInRange` filters by the done time and needs each issue's whole log. The commands call `metricEvents()` with no range, never with `--since` or `--until`.
6. **`tracker.scope.workspace` requirement for Linear.** The Linear descriptor's `configProblems` adds it when an EPC-5 issue registers the adapter. Here a test descriptor shows the hook.
7. **The mirror reuses the golden cases.** `FIXTURES`, `CASES` and `takesDryRun` move from `scripts/goldens.test.mjs` to a new `scripts/golden-cases.mjs`, unchanged. `goldens.test.mjs` already checks that `CASES` covers every command, so the mirror covers every eligible command with no second list.
8. **The mirror includes the git host commands.** Every fixture has `git_host.system: none`, so `issues branch` and the `pr` commands fail the same way on both copies. The mirror runs every command that is neither `local: true` nor `exempt`.

## Review focus

1. A workspace pasted as a URL, such as `https://linear.app/acme`, or typed with capitals. The user expects one problem that names the URL key form. Task 1 pins it.
2. A mapping key typed with a hyphen, such as `in-review`. The user expects a problem that names the key, not a silent no-op. Task 1 pins it.
3. `migrate` on a hosted repository that still has an old `.issues/` folder. The user expects `NOT_SUPPORTED` and no file change, not a migration. Task 7 pins it.
4. An operation that rejects inside a `try` block, such as `listStatusUpdates` in `risks`. The user expects the same warning and problem entry as a synchronous throw. A missing `await` inside the `try` would crash instead. Task 7 pins it.
5. A hosted user whose git email matches no member and who has no `PMKIT_USER`. The user expects `NOT_CONFIGURED` with a next step that names `PMKIT_USER` and `pmkit discover`, not `.issues/config.yaml`. Task 7 pins it.
