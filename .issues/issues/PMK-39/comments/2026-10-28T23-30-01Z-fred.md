# PMK-39 Linear sandbox contract run implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans, as the user picks, to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the tracker contract suite against the Linear sandbox workspace through one fixed test team, with a write guard, a request budget, a cleanup command and the live probes the PMK-35 to PMK-38 specs left open. `npm test` keeps running with no network.

**Architecture:** `scripts/lib/linear/sandbox.mjs` holds the test-team helper (`TEST_TEAM`, `preflight`, `findOrCreateTestTeam`, `waitForCycles`, `listTestTeamItems`, `trashTestTeamItems`, `createGuardedFetch`). PMK-41 reuses it. `scripts/lib/linear/contract-live.mjs` (name outside the `*.test.mjs` glob) is the opt-in entry: it gates on the environment, builds the config, calls `runTrackerContract` with a live `setup`, runs the probes and offers the `cleanup` mode. `sandbox.test.mjs` tests the helper over a scripted fetch. The guard, the budget and the sweep are proven in `npm test` before any live call.

**Tech stack:** Node.js ESM, `node:test`, `node:crypto` `randomUUID`, the PMK-30 client (`createLinearClient`, `isMutation`, `operationName`), `runTrackerContract` from `scripts/contract-suite.mjs`, `createLinearTracker`.

**Spec:** `docs/superpowers/specs/2026-10-28-pmk-39-linear-sandbox-contract-design.md`

## Global constraints

- `npm test` opens no socket. Tests of the helper inject a scripted fetch. `package.json` gains no dependency (ADR-0003).
- The live run writes only in the test team `pmkit-test` (key `PKT`, marker `pmkit-contract-team`), never edits or deletes it, and never creates a label.
- The key never appears in output, an error, a file or a command line. Tests use `FAKE_KEY`. Nobody reads or prints `.env`.
- Private names: the repository is public. No file, commit or comment holds the real workspace URL key or team key. Examples use `acme` and `ACME`. Docs say "the sandbox workspace". Live commands use `$PMKIT_LIVE_WORKSPACE`. Task 11 runs the private-name check (`/home/fred/projects/pmkit-worktrees/check-private-names.sh`); hits in the PMK-30, PMK-33 and PMK-43 comment files under `.issues/` are accepted, nothing else.
- Tasks 1 to 11 make no call to Linear. Only Task 12 does, and stage 3 does not run it.
- Weakening a suite assertion so Linear passes is a user decision. A live failure gets an adapter and fake fix with a fake-based test first.
- Every commit message carries `(PMK-39)` and ends with exactly `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Code, comments and messages follow `~/.claude/skills/unslop/SKILL.md`.
- Run one test file with `node --test <file>`. Run everything with `npm test`.

## Task 2: The guard table and the guarded fetch

**Files:** `scripts/lib/linear/sandbox.mjs`, `scripts/lib/linear/sandbox.test.mjs`

`createGuardedFetch({ fetch, workspace })` returns `{ fetch, guard }`. `guard` exposes `open(ids)` (called by `preflight`), `own(kind, id)`, `stop()` and `stats()`. A scripted fetch in the test returns canned JSON and records each request.

- [ ] **Step 1: Failing tests** (one `test` each, no socket):
  - a query passes through;
  - any mutation is refused before `open()`, with `refusing <name>: not in the live run's list` and nothing recorded by the inner fetch;
  - a root field off the list (`teamUpdate`, `cycleUpdate`, `issueLabelCreate`, `teamDelete`) is refused after `open()`;
  - `issueUpdate` on an id not passed to `own('issue', id)` is refused, and passes after `own`;
  - `projectCreate` with a second team id is refused; with exactly the test team it passes;
  - `issueDelete` with `permanentlyDelete: true` is refused;
  - `teamCreate` is refused when `open({ teamExists: true })`, refused with `copySettingsFromTeamId` or `parentId`, refused when the name, key or description marker is wrong, and passes with the inputs of the spec table when the team is absent;
  - each other row of the spec's guard table passes with the run's ids (`issueCreate` with `labelIds` of "Bug"/"Feature" only, `issueRelationCreate`, `commentCreate`, `commentResolve`, `projectUpdateCreate`, `issueArchive`, `issueRelationDelete`, `workflowStateCreate`, `cycleStartUpcomingCycleToday`, `projectDelete`);
  - after `stop()`, suite mutations are refused but `issueDelete` and `projectDelete` of owned ids still pass (cleanup).
- [ ] **Step 2:** `node --test scripts/lib/linear/sandbox.test.mjs`. Expect failures.
- [ ] **Step 3: Implement** the table as data (`RULES[rootField] = (variables, ctx) => reason | null`), reading the document with `isMutation`, `operationName` and a root-field parse from `client.mjs`. Ids a mutation carries in `variables.input` or directly count as owned only through `own()`; client-chosen ids in create inputs are recorded when the create passes.
- [ ] **Step 4:** Run the file. Expect pass.
