# Changelog

## Unreleased

- Fixes the dry-run and customer paths of `/pmkit:backlog:request-queue` (PMK-207). A failed `issues create` dry run (step 5.1) drops that request's decision and says why, as step 5.2 already did for a link: the request stays open and the others go on. A request whose customer has no file and that has no `from` keeps the customer ID in the "asked by" line of its new issue, after the customer name and the `from` text. The scenario now has an entry that runs the Linear path to the triage suggestion (the workspace answers, `request_queue` is absent) and an entry with a failed create dry run and an unknown customer.
- Fixes the review-request and error paths of `/pmkit:issues:inbox-digest` (PMK-206). `pr blockers` keeps team review requests in the new `reviews.requestedTeams` and only users in `reviews.requested`, so a team named like the user never matches the user. The digest reads pull requests of every open issue, not only `in_review`, finds changes to address on pull requests the user wrote, stops and marks reviews not verified on `RATE_LIMITED`, and cuts the derived list of a tracker with no inbox by `since=`. The scenario now has a complete-inbox entry that offers `inbox mark-read` and a rate-limited entry.
- Fixes the ranking and write rules of `/pmkit:backlog:prioritize-by-demand` (PMK-204). The bands cover only the issues with a score above 0, so an issue with no demand never takes a band from one with demand. With customer requests an issue with no demand is also capped: when its priority is higher than the lowest priority proposed to an issue with demand, it is proposed that priority, so it never ranks above one (the weak comments signal never lowers it). A `demand list` problem now carries `about` (`request`, `customer` or `issue`); a customer with no file or a request on an issue that is no candidate is a warning, and only a request file that did not parse, or a problem on a candidate, stops the write. The comments of the issue's assignee (the plan, progress and summary comments of the work command) and delegation comments, and comments by an `agent:` author, do not count as demand; the output says how many were ignored. The mention rule is the one of `issues delete`, now in `scripts/lib/mentions.mjs` (not preceded by a letter or digit, not followed by a letter, digit or underscore; URLs, link targets and paths ignored), read per candidate with `issues list --text <ID>`, so a `hasMore` on one candidate no longer blocks every write on a large Linear team. The customer tie-break counts the `from` of a request. The live scenario checks the whole-token result from the repo, and a new scenario covers a demand problem that concerns no candidate.
- Fixes the Linear and error paths of `release-readiness` (PMK-205). A selector (`--release`, `--milestone`, `--sprint`) reads only what its basis needs, so `--milestone` and `--sprint` no longer fail on Linear with releases on because of the `listReleases` stub (`--release` still needs `getRelease`, a stub there). The automatic pick reads one rung at a time (releases, milestones, active sprint) and stops at the first that has something, so a read it never reaches cannot fail it. When a read it does need fails with a transient error (`RATE_LIMITED`, `UPSTREAM`), or the releases read is the Linear stub, that rung is `releases_not_read`, `milestones_not_read` or `cycles_not_read` in `skipped`, with a `problems` entry and a warning, and the report is incomplete (`ready` is never `true`); with nothing left to pick, that error is the answer. Any other error from a read (`INVALID_INPUT`, `NOT_FOUND`, `CONFLICT`) still stops the command. `--sprint current` on a tracker without cycles is `NOT_SUPPORTED`, with a next step that names `--release` only when the tracker has releases. A basis with no issue, or only canceled ones, has `empty: true` and `ready: null` (never with an open pull request, which makes it `ready: false`), and `empty` is only set after a complete read (a cut read or an issue file that does not parse leaves it `false` and the report incomplete). A release's tag deploy is found past the newest 20 by asking GitHub for the deploys of `<tag>` and `refs/tags/<tag>` (`listDeploys({ ref })`), and a `refs/tags/<tag>` ref matches the tag.
- Fixes the degraded and error paths of the roadmap review and `risks` (PMK-202). A transient error (`UPSTREAM`, `RATE_LIMITED`) listing epics or milestones marks that section `not checked` with its error code in `unavailable`, and no longer shows the late-issues fallback, which stays for `NOT_SUPPORTED`. An unknown milestone delay reads `unknown`, a Linear epic lists each of its milestones by name in `milestones`, and a todo epic started inside the window is no longer unchecked (the rule is shared with `risks`). After `RATE_LIMITED` the per-epic reads stop and the rest are not checked, and a failing capability note is dropped instead of failing the review. `risks` reports an epic whose update read failed in `updatesNotChecked` instead of `no_recent_update`, and its last update reads `not checked`, not `none` (`updatesRead: false`). With the milestone list unread a Linear epic's `milestones` is `null` and its cell `unknown`, with the epic list unread a milestone's `epics` and a possible delay are `null` and `unknown`, a milestone with no due date reads `no due date`, and a rate limit while listing epics or milestones stops the per-epic reads, naming every epic whose reads were skipped.
- Fixes the fallback and incomplete paths of `goals overview` (PMK-203). Without goals, a broken `epic.md` no longer makes the top-level rollup incomplete (on the goals path it still does, because the epic may link to a goal), and a stray file such as `notes.md` in `.issues/goals` is a `note:` and no longer blocks the fallback. The fallback reads archived issues too, so the live children of an archived parent, and the children of a parent file that does not parse, are named in a warning with `complete: false` instead of showing as top-level rows. `goals list` still prints the epic warnings. The command file says "needs an epic" only when `complete` is true.
- Gives the view errors a stable reason (PMK-200). The three `INVALID_INPUT` errors of `views run` carry `details.reason` (`invalid_view_name`, `view_out_of_date`, `view_file_broken`), and `--json` prints it as `error.reason`. `commands/issues/run-view.md` step 4 reads the reason instead of searching `error.message`, so rewording a message cannot break it. `issues/run-view` has a scenario for each branch of step 4 (not found and the three reasons) and for the Linear branch. `views list --json` gives the same `reason` on each entry of `problems`.
- Makes `text redact` trade false positives for no missed secrets (PMK-197). Every value after a `password`, `passwd`, `pwd`, `credential(s)`, `secret`, `token`, `api_key` or `private_key` key with `=` or `:` is replaced in full, to the end of the line (to the next `|` in a table row), or the quoted text when it is quoted, with `=`, `:`, `=>`, `:=`, `==` or `===` as the separator. A number stays only when it is the whole value after a key that names a quantity (`max_tokens`, `token_limit`), a file location (`` `src/a.ts:12` ``, `token.mjs:42-50`, `file.py:42: msg`) stays, and the directory in `PWD` or `OLDPWD` stays. A JSON `"Authorization": "Basic ..."` and the user and password of `curl -u` (new type `curl_user`) are redacted, and only the Markdown that opened before a value keeps its closing mark, so nothing is left unbalanced. The false positives this accepts (`token: expired`, `password: string`) are listed in the spec, and every case of the issue has a probe. With nothing after the key, or a YAML `|` or `>`, the more indented lines below go, measured at the key's column so a diff `+`, a log timestamp or a list `- ` before the key counts and the sibling keys stay. The `-` of a removed diff line is not part of a key, a key may have an index (`secret[0]=`) whose secret word names it (`user[password]=`, `params[:password]`), Markdown around a key does not hide it (`**Password:** x`, `` `DB_PASSWORD`: x ``), `authorization` is a key, a value that opens `{`, `[` or `(` or ends in `\` takes the more indented lines below (formatted JSON, HCL), a closing mark inside a secret (`login(password=Pa)ss`, `login(password=Ab3)!xY9`) is not its end, every value of a mapping under a secret key goes, and the token patterns run after the pairs, so `token: ghp_... extra` is one value counted as `api_key_value`. It gives the same text when run again on its own output.
- Fixes `issues track-agents` on a broken comment and transient errors (PMK-199). A comment file whose frontmatter does not parse (for example a tab) marks its issue `unknown` with a problem and the command goes on, instead of stopping with exit 2. The text no longer says "no open issue is assigned to an agent" when the list is incomplete, a `blocked` row also lists what is not verified, and the incomplete warning names only the causes that happened (it blames GitHub only for a pull request read).
- Fixes `issues bulk` labels, the one-issue error code and the commit-only failure (PMK-196). `label-add` and `label-remove` trim the value, and `label-remove` takes a label that holds a comma (`ui, web`), so it can be removed; `label-add` still refuses one. A one-issue batch keeps the operation's code (`NOT_FOUND`, `CONFLICT`) instead of `INVALID_INPUT`. `--text` of only spaces is refused like `--text ""`, and the next step for a saved view with no narrowing criterion says to save the view again with one, not to add `--label`, which the CLI refuses next to `--view`. `commands/issues/bulk.md` reads a stop midway only from `result.failed`, so an `auto_commit` failure after every write succeeded is reported as a commit failure, not a stop. The saved-view sort test now checks the order.
- Fixes the inbox authors, the unreadable-time fallback and stale docs (PMK-195). A description or criteria item has `by: null`, because the event log does not say who wrote a line, and a mention under a section such as `## Notes` is `in: description`. An event `at` or a comment `created` that is not a time is a problem in `inbox list` (`complete: false`) and in `validate`, and a comment without an author has `by: null`. `inbox mark-read --key` with an unknown key marks the known keys and reports the others in `unknown` and as a warning. The prune keeps the seen key of an item that is still at the tip of another local or remote branch (decided by the comment file, the mention line or the assignment event), and keeps every key, with a `note`, when git cannot read the branches. A comment with an empty `created` is no problem. The `markRead` JSDoc and the test name now match the code.

On a real `issues log-time` write the more-than-a-day note says the time is already logged, and keeps "check the time before you confirm" for the dry run and `issues parse-time`.

- Adds `/pmkit:backlog:prioritize-by-demand` (PMK-68). It ranks the open issues (backlog, todo, triage, or the flags of `/pmkit:issues:find`) by demand. With `demand_signals` native (Local) the score is the accepted requests of `demand list`, an important request counting twice; ties go to more customers, then the older issue. The command dry-runs every `issues update --priority`, asks once on the full preview whatever `write_policy.confirm` says, writes one issue at a time and stops at the first failure listing applied and remaining. No new CLI command.
- Adds `/pmkit:report:release-readiness` and `pmkit release-readiness [--release id | --milestone id | --sprint current|id]` (PMK-69). It reads what is left for a release: the open issues, the open pull requests whose branch belongs to an issue of the release, and the repository deployments (`matchesRelease` marks the ones whose ref is the release tag).
