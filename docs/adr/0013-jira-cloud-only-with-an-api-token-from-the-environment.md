# Jira is Cloud only, with an API token from the environment and one space per repository

The Jira tab of the planning doc left three questions open for the Jira tracker adapter (EPC-7): Cloud or Data Center; a personal API token or OAuth 2.0 (3LO); company-managed or team-managed spaces. The Unified model's Q1 decision D says to reuse existing tokens, and Q5 decision A says tokens come from the OS keychain, env vars or existing CLI logins, never from the repository file. ADR 0005 (Linear) and ADR 0007 (GitHub Issues) answered the same question for their trackers. The facts below were checked on 2026-11-22 against Atlassian's published docs. No Jira credentials exist, so nothing was checked against a live site. The spec is `docs/superpowers/specs/2026-11-22-pmk-74-jira-auth-and-cloud-design.md`, and the owner chose each option on 2026-11-22.

pmkit supports Jira Cloud only. Atlassian ends Data Center on 2029-03-28, when it turns read-only, and new customers cannot buy it since 2026-03-30. On the first request of each run the client reads `GET /rest/api/3/serverInfo`, and a `deploymentType` other than `Cloud` fails with `NOT_SUPPORTED`. The adapter has one code path: REST v3, Agile 1.0 and the Atlassian Document Format.

The credential is a personal API token. The user creates it at id.atlassian.com and exports `JIRA_EMAIL` and `JIRA_API_TOKEN`. The client reads both from the `env` that `run(argv, { env })` passes in and sends `Authorization: Basic base64(email:token)` up front, because Jira sends no challenge. One module, `scripts/lib/jira/credential.mjs` (PMK-75), is the only reader of the two variables. pmkit stores no credential anywhere. Tokens created since 2024-12-15 expire after 1 to 365 days, so a 401 may mean an expired token. This decision covers classic (unscoped) tokens. Atlassian documents scoped and service-account tokens only through `https://api.atlassian.com/ex/jira/<cloudId>`, which PMK-75 checks on a live site once credentials exist.

A repository uses one Jira site and one space. `tracker.scope.site` holds the site's full host, such as `acme.atlassian.net`, so a custom Atlassian domain works too. `tracker.scope.space` holds the space key, such as `ENG`, as `tracker.scope.team` does for Linear. Requests go only to the configured site, which pins it. Discovery reads the space's style, company-managed or team-managed, and reads statuses, work types and fields for that one space, so both styles map through the existing mapping shape.

## Considered options

- Cloud only. Chosen. One auth header, one REST version and one document format, for the product Atlassian keeps.
- Cloud and Data Center 8.14 or later. Rejected. Data Center needs a personal access token sent as `Bearer`, REST v2 and wiki markup instead of the Atlassian Document Format, so every operation and the test fake would need a second path, for a product that turns read-only on 2029-03-28.
- Personal API token from the environment. Chosen. It adds no stored secret, no refresh and no server, and it works the same in a terminal, in CI and in scheduled runs, as ADR 0005 does for Linear.
- OAuth 2.0 (3LO). Rejected for EPC-7. It needs an app registered in Atlassian's developer console and shared by pmkit's maintainer, a `client_secret` on every code exchange and refresh that a local CLI cannot keep secret, no PKCE, and rotating refresh tokens that pmkit would have to store. Atlassian also tells tools not to have customers create their own 3LO apps.
- The login of the official Atlassian CLI (`acli jira auth login`). Rejected. `acli` has no raw REST command like `gh api`, so pmkit could only read the token `acli` stores, a file pmkit does not own.
- OS keychain or a key file. Rejected, as in ADR 0005: the keychain has no common reader across macOS, Linux, Windows and WSL, and Q5 rules out a secret in a file.
- One space per repository. Chosen. It matches one team per repository on Linear and keeps the config and every list command unchanged.
- Several spaces per repository. Rejected. It changes the config shape and every list command, for a need no EPC-7 issue states.

## Consequences

- Security. The token and the header never appear in output, in a command-line argument, in an error message or its `details`, in a cache file or in the transcript. `/pmkit:setup` never asks for them, and pmkit reads no `.env` file. PMK-31's refusal of secret-like config keys (`token`, `api_key`, `secret`, `password`) applies to Jira too.
- Error mapping. Missing `JIRA_EMAIL` or `JIRA_API_TOKEN`, HTTP 401, a CAPTCHA (`X-Seraph-LoginReason: AUTHENTICATION_DENIED`) and HTTP 403 are `AUTH`. The 401 message says the token may have expired. A non-Cloud `deploymentType` is `NOT_SUPPORTED`. HTTP 429 is `RATE_LIMITED`. Network failures and HTTP 5xx are `UPSTREAM`.
- Authorship. Every write appears in Jira as the token's owner. The adapter resolves `me` and the actor from `GET /rest/api/3/myself`, not from `git config user.email`.
- PMK-75 adds `scripts/lib/jira/credential.mjs` with `jiraCredential(env)`, and builds `createJiraClient({ env, site, fetch })` so `npm test` injects a fake `fetch` and opens no socket. It runs the `myself` and `serverInfo` check on the first request, applies the error mapping, and tests that a fake token appears in no output. It checks scoped tokens on a live site; if one fails against the site host, a new ADR decides the `api.atlassian.com/ex/jira/<cloudId>` path.
- PMK-76 makes `discover --json` return `auth: { source, viewer, site }` first, fails with `NOT_SUPPORTED` on Server or Data Center, and reads company-managed and team-managed spaces alike. PMK-76 adds `tracker.scope.site` and `tracker.scope.space` to the schema and the loader, required when `tracker.system` is `jira`.
- PMK-77 to PMK-80 reach Jira only through the PMK-75 client. No other module reads the two variables.
- `/pmkit:setup` runs `discover --json`. On `AUTH` it tells the user to create an API token at id.atlassian.com and export `JIRA_EMAIL` and `JIRA_API_TOKEN` in the shell profile or in `~/.claude/settings.json` under `env`, never in a file inside the repository, then to run setup again. On `NOT_SUPPORTED` it says pmkit supports Jira Cloud only. On success it writes `tracker.scope.site` and `tracker.scope.space`.
- Cost. A token has the full rights of its owner, and a token in the shell profile reaches every process the user runs, as a `gh` login does. Users renew the token at least once a year.
- Left open: scoped and service-account tokens, for PMK-75; the Bitbucket Cloud credential, for PMK-81.
