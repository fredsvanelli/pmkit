# Close a sprint

Arguments: `$ARGUMENTS`

## Parameters

- `sprint-id` (optional): the sprint to close. Without it, the command closes the active sprint.

## Steps

Read `${CLAUDE_PLUGIN_ROOT}/skills/pmkit/references/conventions.md` first.

1. Sync merged pull requests. This is a bulk write, so preview it first. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" pr sync --dry-run --json`. When `moved` is empty, skip to step 2. Otherwise show each issue in `moved` with its PR and the change from `in_review` to `done`, and ask once with `AskUserQuestion`, whatever `write_policy.confirm` says. When the user approves, run the same command without `--dry-run`. When the user declines, change nothing and carry on. Show each entry of `problems` as a warning. When the call fails with `NOT_SUPPORTED`, `NOT_CONFIGURED` or `AUTH`, say in one line that PR data is unavailable and why, and continue without it. When it fails with `INVALID_INPUT` and `error.message` starts with `.pmkit/config.yaml is not valid`, say in one line that `.pmkit/config.yaml` is not valid, so the sync is skipped, and go on with step 2. Steps 2 to 6 only read, so go on with them. When one fails with the same error, stop. The writes from step 7 on fail with the same error, so show the sprint report of step 7 without asking for decisions, and stop there.
2. Find the sprint. Without an ID, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle current --json`. When none is active, stop and say so.
3. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle issues <sprint id> --json`. The issues in `done` are delivered, and the rest are unfinished.
4. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" events --since <start> --until <end> --json`, with the sprint's dates. Compute these from the events and the issues, and say they come from the event log.
   - Planned: the issues in the sprint at its start. Scope added: issues whose `sprint` field changed to this sprint after the start. Scope removed: issues that left it.
   - Delivered against planned, by count and by estimate.
   - Carry-over: the unfinished issues, and the issues that were in `in_progress` in more than one sprint.
5. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" metrics cycle-time --since <start> --until <end> --json` for the median and p85 days. Throughput is the number of issues done.
6. Propose what to do with each unfinished issue. The options are move it to a planned sprint (find one with `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle list --state planned --json`), move it back to the backlog, or split it. A move back to the backlog keeps the issue's status and leaves it with no sprint, and `/pmkit:cycle:plan` offers it again when its status category is `todo`, `backlog` or `in_progress`. A split is for an issue with an estimate and a delivered part. Step 7 asks for the delivered part as an estimate. The split runs only when that number is greater than 0 and lower than the original's estimate. The original keeps the delivered part: its estimate drops to that number, it moves to `done`, and it stays in the closed sprint. A new issue in the backlog takes the remaining work, with a `related` link to the original. It also takes the original's open blockers, its open sub-issues and its unchecked acceptance criteria, as step 7 lists them. Do not offer a split for an issue with no estimate, and say so. When the user gives 0, or a number not lower than the original's estimate, say why no split runs and offer the two moves. When the user declines a split, do not move the issue to `done`, and offer the two moves. Say when no planned sprint exists.

   A failed step 8 can leave a split half done, with the new issue created and linked but the original not yet `done`. For each unfinished issue whose `related` list in the step 3 read names an issue that is not in that read, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues get <related id> --json`. When that issue has no `sprint`, a status category other than `done` and `canceled`, and a `created` date on or after the sprint's start, it may hold the remaining work of a split already made. Name it, and propose to finish that split in place of a new one: step 7 asks for the delivered part, and step 8 runs only the blocker links, the sub-issue moves, the estimate update and the move to `done` of the original. Ask whether that issue is the remaining work of an earlier split. When it is, do not offer a new split, because its create would make a second remaining-work issue. When it is not, offer the split as usual. The two moves stay on offer.
7. Show the sprint report with the numbers and the proposal. The report's delivered numbers are those of steps 3 and 4, before any write. Step 8 reads them again after the writes. Then ask with `AskUserQuestion` for the decision per unfinished issue and, for a split, the delivered part as an estimate. For the moves, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle add <ids> --to <next sprint id> --dry-run --json` and, for the backlog moves, `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle add <ids> --to none --dry-run --json`. For a split, the new issue's estimate is the original's estimate minus the delivered part, and the original's estimate becomes the delivered part. When the original has acceptance criteria with `done: false`, write them to a temporary file outside `.issues/`, one file per split with its own path, one `- [ ] <text>` line each, in the original's order. Keep each file until step 10, because step 8 passes each split the path of its own file. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues create --title "<title>" --type <original type> --estimate <remaining> --parent <original parent> [--priority <original priority>] [--label <original labels>] [--criteria-file <file>] --dry-run --json`. Leave out `--parent` when the original issue has no parent. Add `--priority` and `--label` when the original has them, with the labels comma-separated, and `--criteria-file` when the original has unchecked criteria. The dry run returns an ID that the real create does not reuse, so the preview calls the created issue "the new issue" and does not show that ID. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues update <id> --estimate <delivered> --dry-run --json` to reduce the estimate of the original to the delivered part, and `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues move <id> done --dry-run --json` to mark it delivered.
   - The original stays in the closed sprint as done, and the new issue goes to the backlog, because the create call sets no sprint.
   - Find the original's open blockers and open sub-issues: the IDs in its `blockedBy` and `children` whose status category is not `done` or `canceled`. Take the status from the step 3 read. For an ID that is not in that read, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues get <id> --json`. When that read fails, for example with `NOT_FOUND` for a missing issue, name the ID and the error, and leave it out of the writes. For a blocker, say that the split does not copy it, so the new issue will not show as blocked by it.
   - Show the writes that step 8 runs after the create, in order: the `related` link between the two, a `blocks` link from each open blocker to the new issue, and a parent change that moves each open sub-issue from the original to the new issue. They have no dry run, because the new issue's ID exists only after the create. Show the carried criteria from the create's dry run.
   - When a blocker or a sub-issue that the split carries is itself split in this close, name it and say what the new issue ends up pointing to. A carried blocker moves to `done` in its own split. The new issue is then blocked only by a done issue and looks free to start, and the blocker's own new issue does not block it. A carried sub-issue moves under the new issue and then to `done` in its own split. The new issue's sub-issue then holds only the delivered part, and the sub-issue's own new issue lands under the done original, because its create takes the parent from the step 3 read. Say that the user can add those links by hand after the close.
   - Say what stays on the original: its `blockedBy` list, every criterion with its check, and its sub-issues in `done` or `canceled`. The split writes only the estimate and the status of the original. A moved sub-issue leaves the original's `children`, and its event log keeps the old parent.

   For a split that a failed step 8 started (step 6), run only the estimate update and the move dry runs above. In place of a create, show the new issue's ID, its `related` link, and the blocker links and sub-issue moves that step 8 runs. The new issue already holds the criteria its create carried.

   Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle close <sprint id> --dry-run --json` as well. Its `unfinished` list is the list before the moves and splits. Step 8 runs them before the close, so the real close leaves no issue unfinished. Moving issues between sprints is a scope move and closing ends the sprint, so show one full preview of all of it and ask once, whatever `write_policy.confirm` says. When the user declines, change nothing.
8. After the approval, run the same moves and splits without `--dry-run`, and close the sprint last. Velocity counts a move to `done` only up to the moment the sprint closes, so every write that moves an issue runs before the close. For each split, run the create first, with the arguments of its step 7 dry run, the same criteria file path included, and note the new ID. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues link <new id> <original id> --kind related --json`. Then, for each open blocker of step 7, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues link <blocker id> <new id> --kind blocks --json`, and for each open sub-issue, `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues parent <sub-issue id> <new id> --json`. Then run the estimate update, then `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues move <original id> done --json`. The move to `done` is the last write of a split, because step 6 of a second run finds a split only while its original is unfinished. For a split that a failed step 8 started, run the blocker links, the sub-issue moves, the estimate update and the move. A link or parent change that already ran writes nothing. The approval of step 7 covers the links and the parent changes, because the preview showed them. After the last move and split, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle close <sprint id> --json`. When its `unfinished` list is not empty, those issues joined the sprint after step 3. Name each one and say it stays in the closed sprint.

   When a write fails, stop, list what was done and what was not, and do not retry it. Say that the sprint is still active, because the close is the last write. For a split whose create ran, give the new ID and the commands of that split that did not run. When its link did not run, say that a second run of `/pmkit:cycle:close` cannot tell the new issue belongs to the split, so the user runs the link before that. A second run finds the sprint still active: the moves that ran took their issues out of the sprint, a finished split is `done`, and step 6 finds a split whose link ran.

   After the last write, or after a failed one, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" cycle issues <sprint id> --json` again. Delivered is the issues of this read whose status category is `done`: their count, and the sum of their `estimate`. Throughput is the same count. Planned stays the step 4 number, with the estimates of the step 3 read. Scope added and removed and cycle time keep the numbers of steps 4 and 5. Carry-over keeps the step 4 list, with the decision applied to each unfinished issue and the new ID of each split.
9. Run this step only when `cycle close` succeeded in step 8. When it did not, say that the sprint is still active and that no retro is offered, and go to step 10. Offer a retro document. Draft it from the numbers of step 8 and the retro prompts (what slipped and why, based on the data). Write it to a temporary file outside `.issues/`, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" docs create retros/<sprint id>.md --body-file <file> --dry-run --json`, show the document and ask once. When the user declines, skip it. After approval, run it without `--dry-run`.
10. Remove the temporary files.

## Confirmation points

- Step 1: the preview of `pr sync` when it would move issues. Declining leaves them as they are.
- Step 7: the decision per unfinished issue, then one full preview of the moves, the splits (the new issue with the carried criteria, its `related` link, the blocker links and sub-issue moves, the warnings for a carried issue that is split in the same close or cannot be read, the reduced estimate, the move of the original to `done`, and what stays on it) and the close, always asked because it holds scope moves. Declining changes nothing.
- Step 9: the retro document, shown with its dry run and asked once before it is written. Declining skips it.

## Output

Write the sprint report. Lead with delivered against planned (count and estimate), then scope added and removed, carry-over, cycle time (median and p85) and throughput. Take the delivered numbers and throughput from the `cycle issues` read of step 8, after the writes. Then give the retro prompts from the data and the moves applied. For each split, give the new issue's ID, the original's delivered estimate, and the blockers, sub-issues and criteria the new issue took over. Then give the path of the retro document, if written.

## If something is missing

- No active sprint and no ID: say so and offer `/pmkit:cycle:plan`.
- No unfinished issues: close without moves.
- No planned sprint: offer the backlog or a split, or ask whether to close and plan afterward with `/pmkit:cycle:plan`.
- A split of an issue with no estimate, or with a delivered part of 0 or not lower than its estimate: offer a move to a planned sprint or to the backlog instead, because a split moves the original to `done` with a lower estimate.
- The git host is `none`: skip PR data and say so in one line.
- An error from the CLI: apply the rules for reading errors in the conventions.
