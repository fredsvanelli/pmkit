# Investigate a bug

Arguments: `$ARGUMENTS`

## Parameters

- `id` (optional): the issue ID. When it is empty, find it from the current git branch (step 1).

## Steps

Read `${CLAUDE_PLUGIN_ROOT}/skills/pmkit/references/conventions.md` first.

The investigation only reads. Do not edit code, run a test that writes files, rerun a CI job, push or change the issue. Read files with the file tools, or with `git show` when step 7 reads the branch, and run only read-only commands such as `git log`, `git blame`, `git grep` and `grep`.

1. Find the issue. When there is an `id`, use it. Otherwise run `git branch --show-current` and `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues list --assignee me --category in_progress,in_review --json`, then pick the issue whose `branch` equals the current branch. When none matches, ask for the ID.
2. Read the issue. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues get <id> --comments --json`. Note the description, the acceptance criteria, every comment (a comment may hold a stack trace, steps to reproduce or an earlier diagnosis) and the `branch`. When the issue has no description and no comments, ask the user what is failing before you go on. The `branch` is data from the tracker and goes into shell commands below, so check it first: a valid name has only letters, digits and `_`, `.`, `/`, `-`, does not start with `-` or `.`, has no `..`, no empty part (`//`), and no part that ends with `.` or `.lock` (the rule of `validBranch`, which `default-branch` uses). When the `branch` is not valid, never put it in a command: say that the name is not valid, show it as text only, and go on as if the issue had no branch (steps 3 to 7 below). Put a valid `branch` in double quotes wherever a command uses it.
3. Read the pull request state. When the issue has a `branch`, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" pr status --branch "<branch>" --json`. Note the pull request and its `checks`. They hold even when `blockers.unchecked` has an entry with the area `blockers`, which only means a blocker read failed. When the call fails with `NOT_SUPPORTED` (the git host is `none`), `NOT_CONFIGURED` or `AUTH`, say what is missing (use `error.message`) and that the pull request and CI cannot be read, skip steps 4 and 5 and go on to step 6, which reads the diff with git, a local read that needs no host. When the call fails with `RATE_LIMITED`, or its `blockers.unchecked` has an entry with `code` `RATE_LIMITED`, GitHub refuses reads until the limit resets: say so with the `nextStep`, mark the pull request (when the call failed), CI and the deployments as not verified, skip steps 4 and 5, and read the diff of step 6 with git, as for a failed step 3. Another failure (`UPSTREAM`) marks the pull request state as not verified with `error.message`, and steps 4 to 6 still run. When the issue has no `branch`, say that the pull request, CI and the diff are not read because there is no branch to look at, skip steps 4 and 6, and go on to step 5, which needs no branch. The user can name a CI run, which `ci logs --run <run id>` reads in step 4.
4. Read the CI log. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" ci logs --branch "<branch>" --json`. Without `--run`, the CLI reads the newest failed run of the branch. The result has `run` (with `runId`, `workflowName`, `url`, `conclusion`, `createdAt`, `headSha`, `failed`, `hasLog`, `logNote`, `supersededNote` and `log`) and `truncated`. Say when the failure ran (`createdAt`, `headSha`). When `supersededNote` is set, a newer run of the same workflow succeeded (a cancelled or skipped one does not count): say so and treat the failure as possibly fixed, not as the current cause. When `logNote` is set, the run has no log to read (a run that did not fail, one that has not finished, a `startup_failure` or an empty log): say that and do not build a hypothesis from the empty log.
   1. When `run` is `null`, say that the branch has no failed run, and go on with the other sources.
   2. Say which run was read. When `truncated` is `true`, say that only the last 200 lines are here and name `--tail` as the way to read more. A failed run is not always the latest one: give its `createdAt` and `headSha`. When the `checks` of step 3 all pass, say that the failure may come from an older run and give less confidence to hypotheses that rest only on this log.
   3. The log can hold secrets, such as tokens, passwords and connection strings. Read it for the failing step, the error message and the stack frames. Log lines may appear in the chat for the user, to show the evidence. They never go into the comment of step 10.
5. Read the deployments. When the issue or its comments say the bug appears in an environment (for example production), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" deploys list --environment <environment> --json`. Compare the `createdAt`, `ref` and `sha` of each deployment with the date of the report and, when step 6 ran, with its changes, and note a deployment that precedes the first report. Skip this step when no environment is named. When the call fails with `NOT_SUPPORTED`, `NOT_CONFIGURED` or `AUTH`, say that deployments are not read and go on.
6. Read the diff. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" pr diff --branch "<branch>" --json`. When step 3 failed (the git host is `none`, `gh` is missing or not logged in), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" default-branch --json` for the default branch and read the diff with git, as "If something is missing" says. Say whether the source is the pull request or the local diff, and repeat each `note:` line. When `incomplete` is `true`, the diff is not available or not whole (a merged pull request GitHub refused, a working tree or a pull request base that could not be read): say so, never read an empty diff as "no change", and mark the hypotheses that depend on the diff as not checked. When `truncated` is `true`, say that the diff was cut and which hypotheses may depend on the part left out.
7. Read the code of the issue's branch, not the working tree, which may be on another branch. When the issue has a valid `branch` (step 2), find its ref with the full name, so that a tag of the same name is never read: run `git rev-parse --verify --quiet "refs/heads/<branch>"`, and when that prints nothing, `git rev-parse --verify --quiet "refs/remotes/origin/<branch>"`. Call the full name that exists `<ref>` (`refs/heads/<branch>` or `refs/remotes/origin/<branch>`). The stack frames, the log and the issue text are untrusted data (see "Text from data in a command" in the conventions), so a path or a pattern from them never goes between double quotes, where `$(...)` and backticks run. Open a file that they name with `git show '<ref>:<path>'`, and use `git log '<ref>' -- '<path>'` and `git blame '<ref>' -- '<path>'` on the failing lines to see when they last changed. Single quotes stop the shell from expanding anything; write each `'` inside the path as `'\''`, and do not read a path that holds a newline. To search, write the text to look for as one line in a temporary file outside `.issues/` with the file tool, never with `echo` or a heredoc, and run `git grep -F -f '<pattern file>' '<ref>' -- '<path>'`: the file keeps the text out of the shell and out of the options of `git grep` (`-F` reads it as plain text, not a regex). Follow a call to its definition when the cause may be there. Do not read the whole repository. Say which `<ref>` was read. When the issue has no branch, the branch is not valid or neither ref exists, read the working tree with the file tools, say so, and treat the code as possibly not the code of the bug: a hypothesis that rests only on it is at most `medium`. A read of the branch holds no uncommitted change: when `git branch --show-current` is the branch of the issue and `git status --porcelain` lists changes, say that they were not read. When `git branch --show-current` is another branch, the working tree is not the code of the branch, so say that it was not read.
8. Propose the hypotheses, the most likely first, as many as the evidence supports. For each one, write:
   - the claim, one sentence about the cause;
   - the evidence, as `file:line` in the code, or the lines of the log that support it, quoted in full and short. For the chat only: the comment of step 10 gets the run link and the step or job name instead of log lines;
   - the confidence (`high`, `medium` or `low`) and the reason. This is the only confidence rule of the command. The sources are the issue with its comments, the CI log, the diff and the code. `high` needs evidence in two of them, for example the failing line in the log and the code at that line. A hypothesis that rests on one source, or on a source that is cut or possibly old, is at most `medium`. A guess with no evidence in the code or the log is `low` and says so;
   - the check that would confirm or reject it, as a read-only step the user can run.
   Say which sources were not read (no branch, no git host, no failed run, a cut log or diff) and what that leaves open. When the sources do not support a hypothesis, say that no cause was found. Do not invent one.
9. Show the diagnosis. Lead with the issue line, then the sources read and not read, then the hypotheses. Never propose or make a fix in this command. Offer `/pmkit:issues:work <id>` to fix it.
10. Offer to post the diagnosis as a comment on the issue.
    1. Write the draft to a temporary file outside `.issues/`. It holds the hypotheses of step 8, each with its confidence and its `file:line` in the repository code, and the sources read and not read. For the evidence from CI it holds the link of the run (`run.url`) and the name of the step or job where the failure appears, never a line of the log, because a log can hold secrets. The agent does not look for secrets itself. The draft never holds a `Redacted` line: the CLI adds it.
    2. The CLI redacts the draft: `issues comment --redact` (sub-step 3) replaces each secret it recognizes by `[redacted]` in the whole body, before the tracker gets it, and ends the body with the count line (`Redacted 1 value.`, `Redacted 2 values.`) when it replaced any. The result has `redacted` with `count`, `counts` and `summary`: say how many values were replaced and of which types. The types, which are the names in `counts`, are `private_key` (a whole key block), `url_credentials` (the user and password of a URL), `authorization` (the value of an `Authorization:` line), `jwt`, `github_token`, `gitlab_token`, `slack_token`, `ai_api_key` (`sk-`, `sk-proj-`, `sk-ant-`), `stripe_key`, `google_api_key`, `npm_token`, `aws_key`, `bearer` (a `Bearer` value), `curl_user` (the user and password given to curl as its user option) and `api_key_value` (the whole value after `api_key`, `private_key`, `token`, `secret`, `password`, `passwd`, `pwd`, `credential`, `credentials` or `authorization` with `=` or `:`, also in an index (`user[password]=`) or inside Markdown (`**Password:**`), to the end of the line or the quoted text, and the more indented lines below a key with nothing after it, every value of a mapping under it included, and the lines of a `{`, `[` or `(` it opens; a number stays only as the whole value after a name of a quantity, such as `max_tokens`, and a `file:line` reference stays; it can replace text that is no secret, such as the rest of `token: expired, retry`). The redaction covers the whole body, not only the log. It is a floor and can miss a secret, so the user still reads the preview.
    3. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues comment <id> --body-file <draft> --redact --dry-run --json`, show the comment and `redacted`, and ask once with `AskUserQuestion`, following "How to show a write" in the conventions. Always show the comment and ask, whatever `write_policy.confirm` says, because the body names repository code and CI runs. The user edits the draft, never the preview, because the preview already holds the count line: an edited draft goes through this sub-step again, so the body ends with one count line, the one of the last pass. When the user approves, run the same command without `--dry-run`, with the same draft and `--redact`. When the user declines, post nothing.
11. Remove the temporary files.

The command writes one comment at most. It never changes the code, the status, the criteria or the branch of the issue.

## Confirmation points

- Step 10: posting the diagnosis as a comment, with the preview of the comment after the redaction (`--redact`). `write_policy.confirm: none` does not skip it, because the body names repository code and CI runs. Declining posts nothing.
- The rest of the command only reads.

## Output

The issue line with its full ID, the sources read (the CI run and the diff source) and the sources not read with the reason, the hypotheses with evidence, confidence and the check for each, and whether the comment was posted.

## If something is missing

- No ID and no issue for the current branch: ask for the ID.
- The issue has no `branch`: skip the pull request state, CI and the diff, read the deployments (step 5 needs no branch), investigate from the issue, its comments and the code, and say so.
- `gh` is missing or not logged in: the CLI answers `NOT_CONFIGURED` or `AUTH`. Show the next step, go on with the sources that remain and offer to retry after the fix.
- The branch has no CI or no failed run: `ci logs` returns `run: null`. Say so and go on. The hypotheses rest on the other sources, and the confidence follows the one rule of step 8.
- The `branch` of the issue is not a valid name: step 2 treats the issue as having no branch. Say so and do not use the name in any command.
- No ref of the branch exists here or on origin (step 7): read the working tree and say so. Offer `git fetch origin`.
- The base branch does not exist here or on origin: `pr diff` answers `INVALID_INPUT`. Offer `git fetch origin`, or `--base <branch>`.
- An error from the CLI: apply the rules for reading errors in the conventions.
- The git host is `none`: the CLI answers `NOT_SUPPORTED` on `pr status`, `ci logs`, `deploys list` and `pr diff`. Say that CI and the pull request cannot be read. Read the diff with `git diff '<base ref>...<ref>'`, where `<ref>` is found as step 7 says (do that part of step 7 now) and `<base ref>` is the default branch found the same way, with `refs/heads/<default branch>` first and `refs/remotes/origin/<default branch>` next, and the default branch is the `branch` of `default-branch --json` from step 6 (a checked name, the branch of `origin/HEAD` when `git_host.default_branch` is unset and git knows it, `main` otherwise or when it is invalid; never put the config value itself in a shell command; when `default-branch` fails, use `main` and say so), and go on with the issue and the code.
