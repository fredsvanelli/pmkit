# Record a decision

Arguments: `$ARGUMENTS`

## Parameters

- `decision` (optional): what was decided and why, in the user's words. When it is empty, ask for it.
- `issues` (optional): the IDs of the issues the decision affects. When it is empty, suggest the issue of the current branch and ask which others apply. A decision may have no related issue.

## Steps

Read `${CLAUDE_PLUGIN_ROOT}/skills/pmkit/references/conventions.md` first.

1. Collect the decision. Keep the user's words. Ask for what is missing: the context that forced the choice, the alternatives that were rejected and the consequences the user already knows. Do not invent a consequence or an alternative. Ask once whether the decision replaces older ADRs, and which ones by their numbers; a decision may replace several. Skip the question when the arguments or the user's words already name them (for example "it replaces ADR 0002"), and never ask again for a number the user named. Take only what the user says: never look for a replaced ADR in the text of the other ADRs. When the answer is no, the rest of this command runs as if there were no older ADR. Pick a short title in the user's words.
2. Check the related issues. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues get <id> --json` for each one. When an ID does not exist, the CLI answers `NOT_FOUND`: stop before any write and ask for a corrected ID. When the decision replaces older ADRs, find each one too. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" docs adr-get <old number> --json`. It only reads and returns `number`, `title`, `status`, `path`, `ref` and `place`. Show its `notes`, which say when the ADR holds two different statuses. `NOT_FOUND`, `CONFLICT` and `INVALID_INPUT` stop the command before any write: show `error.message` and ask for another number. The older ADR is the one this call names, so keep its `number` and its `ref`. `ref` is the path without the display label `tracker:` that `path` carries for a tracker outside the repository, so the Supersedes line never gets that label; for a tracker outside the repository it is the path from the repository root (`../...`), which a reader can open. When `status` already says superseded by another ADR, tell the user that step 7 would replace that mark, and ask whether to go on.
3. Pick the place and the number. Write the title to a temporary file outside `.issues/` (one line, as the conventions say for files with text from data). Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" docs next-adr --title-file <title file> --json`. The CLI computes the number, the slug and the path, so do not work them out yourself. `destination` is `repo` for the repository file `docs/adr/NNNN-<slug>.md` (the repository has its own `docs/adr/`, or the tracker cannot create documents, as on Linear) and `tracker` for a tracker document that `docs create` writes at `docPath`, so `auto_commit` applies. With `tracker.path: .` the tracker's `docs/adr/` is the repository's, and `destination` is `tracker` even when the folder exists: write it with `docs create`, never with the file tools. On Linear, say in one line that the ADR is a Markdown file in the repository, because the tracker cannot create documents. `INVALID_INPUT` means the title has no letter or digit, so ask for another title. Show every line of `notes`. Then, when `gitHost` is not `none`, run `GIT_TERMINAL_PROMPT=0 git fetch origin <defaultBranch>` (the CLI returns only a valid branch name, `main` with a note otherwise) with a limit of 20 seconds and run `docs next-adr` again, so the number sees the ADRs merged meanwhile. When the fetch fails or times out, go on: the CLI reads the `origin/<defaultBranch>` that is already here and says so in `notes`. With `gitHost: none`, skip the fetch. Then compare numbers: when a replaced ADR's number is higher than the new `number`, warn that the older ADR is newer than the decision that replaces it, and ask whether to go on or to correct the number the user named. Run the same comparison again when step 5 changes the number.
4. Draft the ADR in the format of the ADRs already in the folder. Read the newest one with the file tools and follow it. When the folder has none, use the format of `docs/adr/` in this repository: the title as the first heading, one paragraph with the context, the decision and why, `## Considered options` (only when the user named rejected alternatives) and `## Consequences`. When the decision replaces an older ADR, put one line `Supersedes: ADR <old number>, <old ref>` per replaced ADR, in the order of their numbers, right under the title, or right under a status line when the ADR format puts one there, each with the `number` (zero-padded, as the CLI gives it) and the `ref` kept in step 2, never the `path`, so the new ADR names every ADR it replaces. When it replaces none, write no such line. Add one section at the end, `## Related issues`, with the full IDs one per line, or `none`, because that is how the ADR points back to the issues. Write the draft to a temporary file outside the tracker folder.
5. Confirm and write. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" docs next-adr --title-file <title file> --json` once more right before the write. When `number` or `path` changed, tell the user, update the file name and the draft, and treat the new path as the one to confirm. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" docs create <docPath> --body-file <file> --dry-run --json` for a tracker document, show it, and ask once with `AskUserQuestion`, whatever `write_policy.confirm` says, because an ADR is a permanent record. For a repository file there is no dry run, so show the path, the number, the slug and the full text and ask once. Ask again after every change of the number or the path. When the user declines, stop and change nothing. After approval, run the same `docs create` command without `--dry-run`, or write the repository file with the file tools. `CONFLICT` from `docs create` means the path appeared meanwhile: go back to this step.
6. Link the issues. Skip this step when there is no related issue. Each related issue gets a comment with the number, the title and the `path` of the result of step 5, written to a temporary file. When `destination` is `tracker` and a note says the tracker folder is outside the repository, `path` starts with `tracker:` and is relative to the tracker folder, so the comment cites `docPath` instead and says it is a document of the tracker, not a file of the repository. When `destination` is `repo`, the comment also says that the file is on the branch of the current work until it merges. For each issue run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues comment <id> --body-file <file> --dry-run --json`. When `destination` is `repo`, say before the preview that the ADR file has no commit yet, so the comments point to a file that exists only in this working tree until the user commits and pushes it. One issue is a single write: show the comment and ask once, unless `write_policy.confirm` is `none`, which skips that question. More than one issue is a bulk change: show every comment first and ask once, whatever `write_policy.confirm` says. When the user declines, post nothing and say that the ADR is written and not linked. After approval, run each command without `--dry-run`, in the order of the IDs.
   Then record the link on each issue too, so a read lists the issue's decisions. For each issue run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" issues update <id> --add-doc <path> --dry-run --json`, with the same path the comment cites. On Linear the link is an attachment on the issue that points to the file on GitHub (`git_host.repo` and the default branch), so it needs a GitHub repo in `.pmkit/config.yaml`. When the first dry run answers `NOT_SUPPORTED` or `NOT_CONFIGURED` (no GitHub repo, `/pmkit:link-repo` sets it), skip this part for every issue and say that the comment is the link there. When it answers an error about unknown docs (Linear refused to read them), skip that issue, say so and keep it in the list of what is missing. Otherwise show the `docs` before and after of every issue and ask once more under the same rule as the comments: one issue is a single write, more than one a bulk change. After approval, run each command without `--dry-run`, in the order of the IDs. When a comment or a `docs` update fails, stop step 6 there: do not retry, do not run the rest of the comments or links, and do not delete the ADR. Step 8 lists what changed and what is left.
7. Mark the older ADRs. Skip this step when the decision replaces none, or when the new ADR was not written (step 5 declined or `docs create` failed). A failed comment or `docs` link of step 6 stops step 6, not this step, since it depends on neither. When step 6 stopped on a failure, say so first, with the issue and the error, and then ask about the older ADRs: the failure does not cancel the marks. For each older ADR, in the order of their numbers, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/pmkit.mjs" docs adr-status <old number> superseded --by <new number> --dry-run --json`, with the number of the ADR written in step 5. Show `path`, `place`, `status.before`, `status.after` and every line of `notes` of every ADR, and ask once with `AskUserQuestion`, whatever `write_policy.confirm` says, because the status of an ADR is a permanent record. Two or more ADRs are a bulk change: show every preview first, then ask once. When `place` is `repo`, say that the file has no commit until the user commits it. After approval, run each command without `--dry-run`, in the same order. When a call fails, stop there: do not run the rest, and list the ADRs marked and the ones left. When the user declines or a call fails, leave the older ADRs that are not marked as they are, keep the new ADR and its Supersedes lines, and say that each of them is not marked: offer `/pmkit:spec:adr-status <old number> superseded --by <new number>` for each one.
8. Report a failure of step 6, after step 7 has run or been skipped. Step 6 already stopped at the failed write. List the issues that got the comment and the `docs` link and the ones that did not, with the error, and offer to run the missing ones again.
9. Remove the temporary files.

Two branches that write an ADR at the same time can pick the same number, and git does not report it because the slugs differ. When a merge leaves two ADRs with one number, the later PR renames its file to the next number from `docs next-adr` and updates the comments it posted.

## Confirmation points

- Step 5: the ADR, its path and its text. `write_policy.confirm: none` does not skip it. It asks again when the number or the path changes before the write.
- Step 7: the new status line of the older ADR, or the previews of all the older ADRs, asked once. `write_policy.confirm: none` does not skip it.
- Step 6: one comment, as a single write (`write_policy.confirm: none` skips it), or the preview of several comments, as a bulk change (it always asks). Then the `docs` links, under the same rule.

## Output

The ADR number, title and path, which place was used (`repo` or `tracker`, and the line about the degradation on Linear), whether the file has a commit (a tracker document gets one from `auto_commit`, a repository file does not), the notes of `docs next-adr`, and one line per related issue that got the comment and the `docs` link (or that the comment is the only link, on Linear). When a comment or a link failed, the list of what is missing. When the decision replaces older ADRs, for each one the path, its status before and after and whether the user confirmed it, or that it was not marked and the `/pmkit:spec:adr-status` call that does it.

## If something is missing

- No decision text: ask for it. Do not write an empty ADR.
- A related issue that does not exist: `NOT_FOUND`. Ask for a corrected ID, and write nothing until all the IDs exist.
- `INVALID_INPUT` from `docs next-adr`: the title has no letter or digit. Ask for another title.
- `NOT_SUPPORTED` from `docs create`: write the file `docs/adr/<filename>` in the repository with the same number and say that the tracker could not create it.
- `NOT_CONFIGURED`, or no `.pmkit/config.yaml`: offer `/pmkit:setup`.
- An error from the CLI: apply the rules for reading errors in the conventions.
